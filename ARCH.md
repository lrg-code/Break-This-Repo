### 2. DCP Packet Header Structure

| Field Name | Bytes | Type/Value | Description | Anti-Tamper/Security Mechanism |
| :--- | :--- | :--- | :--- | :--- |
| Magic | 4 | XOR-obfuscated with random Salt at startup (non-fixed) | Fast protocol identification, no fixed fingerprint | Dynamically changing, Anti-DPI fingerprinting |
| Type | 1 | 0 Probe / 1 SYN / 2 SYN-ACK / 3 ACK / 4 Heartbeat / 5 Data / 6 Update Announcement | Tells receiver how to process the packet | Dropped if checksum fails |
| Flags | 1 | Carry PoW / Require ACK / Sandbox flag | Controls handshake, heartbeat, high-risk file interception | Dropped if checksum fails |
| SessionID | 4 | Randomly generated by initiator | Associates this UDP communication, isolates sessions | Dropped if checksum fails |
| Sequence | 4 | Increments from 0 | Works with sliding window to prevent replay attacks | Dropped if outside window |
| Window | 4 | e.g., 256 | Tells peer how many out-of-order packets can be buffered | Dropped if checksum fails |
| PayloadLen | 2 | Fixed 1024 bytes (including header) | Actual length of subsequent encrypted data | Fixed size resists traffic analysis |
| Checksum | 4 | BLAKE3 | Anti-tamper seal for the entire packet | Dropped if mismatch |

**Supplementary Notes (Table 13 Revision):**
* **Variable Magic:** The first byte of the SYN packet Payload carries a 4-byte Salt in plaintext. Subsequent packets use this Salt to XOR the header, solving the "both sides can't match" problem.
* **Fixed Fragmentation:** Abandon dynamic fragmentation. Unify to 1024 bytes. Use PayloadLen to truncate boundaries, avoiding fingerprint exposure.

### 4. Security Defense System

#### 4.1 Core Attack Defense Matrix

| Threat | Attack Method | Defense Solution | Defense Level |
| :--- | :--- | :--- | :--- |
| Sybil Attack | Attacker runs thousands of fake nodes to fill tunnels | DPoS + 10s heartbeat verification + Reputation reset & reward deduction | ⭐⭐⭐⭐⭐ |
| Replay Attack | Intercepts old broadcast packets and resends them | Sliding window sequence numbers + Drop old packets outside window | ⭐⭐⭐⭐⭐ |
| Eclipse Attack | Forges fake network maps | Multi-source cross-validation: Query 15 nodes, 2/3 (10) consistent views required | ⭐⭐⭐⭐ |
| Exit Eavesdropping | Last hop sees plaintext data | End-to-End Encryption (E2EE): Sender encrypts payload directly with receiver's public key | ⭐⭐⭐⭐⭐ |
| Traffic Analysis (DPI) | Identifies via fixed IP and packet size | CIP rotation + Unified 1024 bytes + Decoy flanking + 0~500ms random delay | ⭐⭐⭐⭐ |

*Topology Hiding (5/1 Rate Limiting):* `find_node` requests from untrusted nodes return only 1/5 of nodes (K=20 reduced to K=4). Combined with request rate limiting, this prevents large-scale crawlers from mapping the entire network in a short time, significantly increasing targeted blocking costs.

### 12. Native Feature Enhancement: Built-in Distributed Storage (Anti-Censorship Persistence)

This is DCP's **killer feature** distinguishing it from Tor/I2P. We don't just communicate anonymously; we make **published information (websites/files) never disappear.**

**12.1 Design Goals**
1. **Publish to Prove:** Upload a `dws:` website, N nodes across the network store a fragment for you.
2. **Access to Spread:** The more visits a site gets, the more copies exist. Censors cannot delete it.
3. **Anti-Abuse:** Cannot let people spam garbage. Must combine **PoS + Proof of Storage**.

**12.2 Core Technical Mechanisms**
* **Content Addressing & Chunking:**
  * Rule: Split `dws:` or `dfs:` large files into **1MB fixed chunks**.
  * Naming: Each chunk name = `BLAKE3(chunk data)` (Content hash).
  * Advantage: Same file stored only once network-wide (auto deduplication). Hash is filename, no one can tamper.
* **Distributed Storage Flow (Publisher View):**
  1. **Storage Node Selection:** Publisher calculates XOR distance between own NodeID and target chunk hash, selects closest **20 online nodes**.
  2. **Storage Request:** Publisher sends `Type=7 (Storage Request)` with data chunk and **PoW Storage Token** (proves you paid computational cost for storage).
  3. **Storage Commitment:** Receiving node verifies PoW, stores chunk, returns signed receipt. Publisher needs **≥10 receipts** to consider "Publish Successful" (200% redundancy).
* **Auto-Repair & Anti-Deletion (Visitor View):**
  1. **Periodic Inspection:** Storage nodes proactively ask neighboring nodes every **1 hour** if the chunk is alive elsewhere.
  2. **Auto-Completion:** If copies <10 (e.g., someone deleted), node auto-fetches from existing copies, **increasing backups**.
  3. **Result:** Unless ALL nodes storing the chunk lose power simultaneously globally, data cannot be completely deleted.

# DCP Relay Node Architecture and Detailed Explanation

**Author:** anon_playerd
**Version:** v1.1 Supplement
**Description:** The DCP network abandons the traditional dual-node direct connection model, dividing all network routers into five types of relay nodes (Type 1~5). This design aims to solve core pain points of traditional anonymous networks (Tor/I2P): weak anti-censorship, NAT traversal difficulties, and node freeloading.

---

### Node Common Attributes
All relay node types contain the following base attributes:
* **NodeID:** Public Key Hash (Self-certifying address)
* **Signing Key:** EdDSA_SHA512_Ed25519
* **Encryption Key:** ECIES_X25519
* **Transport Layer:** UDP (Fixed 1024-byte fragmentation, Dynamic Magic anti-DPI)

---

### Detailed Introduction to Each Relay Type

#### Type 1: Inbound Gateway
* **Core Function:** Receives encrypted packets from external nodes, forwards them to the target node's internal tunnel. Acts as the "receiving door" for data.
* **Key Mechanisms:**
  * **Multi-entry Parallel:** Publishes at least 3 virtual IPs (CIP) in LeaseSet, preventing single entry DDoS.
  * **Anti-DDoS:** Token bucket rate limiting (Same source IP ≤50 SYN/s), silent drop on excess.
  * **Anti-Replay:** Sliding window sequence numbers, strictly rejects old packets.
* **Security Advantage:** Without E2EE keys, inbound gateway cannot decrypt data, can only blindly forward garbage.

#### Type 2: Outbound Gateway
* **Core Function:** Receives data from sender, acts as last hop to forward to the actual target receiver. Acts as the "sending door" for data.
* **Key Mechanisms:**
  * **End-to-End Encryption (E2EE):** Sender encrypts payload directly with receiver's public key, so outbound gateway sees no plaintext.
  * **Fixed Packet Length:** All data blocks unified to 1024 bytes, with random delays, preventing traffic analysis.
  * **Multiplexing:** Backup tunnels transmit fragments in parallel with main tunnels.
* **Security Advantage:** If outbound gateway is malicious, it only sees meaningless ciphertext.

#### Type 3: Relay Node
* **Core Function:** Pure intermediate forwarding node, no direct contact with sender/receiver application layer data. Provides bandwidth and computational power.
* **Key Mechanisms:**
  * **Double-layer Encryption:** Outer layer wraps routing info (hop-by-hop decryption), inner layer wraps E2EE data. Relay only sees previous/next hop IP, cannot link context.
  * **Reputation & DPoS:** Relay must stake tokens (DPoS), earns "Relay Coin" by forwarding data. Malicious behavior, offline, or collusion (collusive ring traffic) results in 20 Reputation Point deduction, or slashing of stake.
* **Security Advantage:** Economic penalty mechanism. Even with thousands of fake nodes (Sybil), high staking cost bankrupts attackers, significantly reducing Sybil risk.

#### Type 4: NAT Traversal Node
* **Core Function:** Helps nodes behind Symmetric NAT or strict firewalls (e.g., home broadband users) establish connections, breaking physical network limits.
* **Key Mechanisms:**
  * **"Simultaneous Open" Mode:** When both parties are behind strict NAT, traversal node acts as third-party coordinator to signal both to send probe packets simultaneously to punch holes.
  * **Encrypted Challenge:** Rewards based on "successful hole punches" and "actual forwarding volume".
  * **Privacy Protection:** Traversal node theoretically sees real IP, so strict high reputation is required, and hole punching requests must contain encrypted instructions.
* **Security Advantage:** Greatly increases survival rate of "orphan nodes", expanding the anonymity set (Anonymity Set). More people = safer network.

#### Type 5: Secret Node / Bridge
* **Core Function:** Similar to Tor Bridge, acts as last escape channel in extreme censorship environments. **Absolutely NOT written into public DHT database.** Distributed only offline (e.g., acquaintances, QR codes, encrypted groups).
* **Distribution Mechanism:** Uses "Multi-source Random Verification (Anti-Eclipse)". User requests 15 nodes, requires 2/3 consistent views, preventing node list pollution.
* **Anti-Freeloading & Anti-Sybil (Core Revision):**
  To prevent secret nodes from "connecting but not transmitting" (freeloading), introduce multiple verification:
  1. **Bidirectional Signed Receipt:** After User A successfully retrieves data via Secret Node, must return a "Data Receipt" signed with A's private key. Secret Node packages receipts for rewards.
  2. **PoW Proof:** System periodically sends high-difficulty math problems to Secret Node, solution must be based on "actual forwarded ciphertext volume in past hour". No work = no valid proof.
  3. **DPoS Slashing:** Becoming a Secret Node requires staking. If found running unauthorized fake nodes (Sybil) or intentionally dropping packets, network slashes staked tokens.
* **Security Advantage:** Breaks "DHT seed total block" extreme case. Even if an entire country's IP block is banned, users with a few overseas secret nodes can 100% connect.

### Summary
DCP's five relay node types form a **"Decentralized, Strong Economic Incentive, Physically Anti-Censorship"** closed-loop system. It inherits Tor and I2P's tunnel encryption mindset, and further improves engineering on **Anti-Sybil (Type 3), Anti-Blocking (Type 5), and Breaking Physical Limits (Type 4).**
